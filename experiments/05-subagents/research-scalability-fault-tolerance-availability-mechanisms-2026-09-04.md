# Research: Scalability, Fault Tolerance, and Availability Mechanisms in Distributed Systems

> Generated: 2026-09-04
> Core question: What concrete, implementable techniques are used to achieve scalability, fault tolerance, and availability in distributed systems, and how do they interact and trade off against each other?

> Scope note: This report is a mechanisms-focused deep dive companion to the prior report `research-distributed-systems-2026-09-04.md` (general primer covering CAP theorem, replication, and sharding fundamentals). It does not re-derive those foundational concepts — it references them briefly where relevant and focuses on the concrete engineering techniques used to achieve each of the three named properties.

## Summary

Scalability, fault tolerance, and availability are related but distinct properties achieved through overlapping but not identical toolkits. **Scalability** is primarily achieved by making services stateless so they can be horizontally replicated behind load balancers, partitioning data (sharding) so no single node bears the full load, and decoupling components with caches and async queues so spikes don't propagate synchronously. **Fault tolerance** is achieved by assuming failure is normal and designing components to isolate, detect, and recover from it automatically — redundancy, health checks, circuit breakers, retries with backoff and idempotency, bulkheads, timeouts, and orchestrator-driven self-healing (e.g., Kubernetes). **Availability** is the observable outcome of redundancy plus fast, automated failure detection and failover across zones/regions, quantified in "nines" that translate directly into a downtime budget. All three interact through cost and consistency trade-offs: more redundancy and geographic spread increases both cost and availability but pushes systems toward eventual consistency (CAP/PACELC), and the practical ceiling on availability is usually not any single technique but the reliability of your riskiest shared dependency (DNS, a single region, a human deploy process). For most production systems, the recommended baseline is stateless horizontally-scaled services + multi-AZ redundancy + automated health-check-driven failover + circuit breakers/retries with jitter + chaos testing to validate it — reserving multi-region active-active and five-nines engineering for workloads where the cost is justified.

## Findings

### Scalability

**Horizontal vs. vertical scaling.** Vertical scaling (bigger machine) is simpler but has a hard ceiling — high-CPU/high-RAM instances are disproportionately expensive and cloud providers cap instance sizes, giving vertical scaling a practical maximum ([USAVPS](https://usavps.com/blog/horizontal-vs-vertical-database-partitioning-practical-strategies-for-scalable-performance/); [dev.to](https://dev.to/matt_frank_usa/database-sharding-horizontal-scaling-strategies-3b07)). Horizontal scaling (more machines) avoids that ceiling but requires the workload to be splittable — which is why it depends on the two techniques below: statelessness for compute, sharding for data.

**Stateless service design + auto-scaling.** Autoscaling works best with stateless, horizontally scalable services; stateful monoliths or apps with in-memory sessions need redesign to benefit ([oneuptime](https://oneuptime.com/blog/post/2026-01-24-configure-horizontal-scaling/view); [Sedai](https://sedai.io/blog/autoscaling-in-eks)). In practice this is implemented as: Kubernetes' Horizontal Pod Autoscaler (HPA) adjusts pod replica counts based on CPU/memory (or custom) metrics, and when HPA needs more pods than existing nodes can host, the Cluster Autoscaler adds nodes, which in AWS EKS are themselves backed by an EC2 Auto Scaling Group ([AWS containers whitepaper](https://docs.aws.amazon.com/whitepapers/latest/containers-on-aws/scaling.html); [AWS EKS multi-AZ blog](https://aws.amazon.com/blogs/containers/amazon-eks-cluster-multi-zone-auto-scaling-groups/)). AWS Auto Scaling Groups perform the equivalent for non-containerized EC2 fleets, scaling instance count to demand ([Spacelift](https://spacelift.io/blog/aws-scaling)).

**Sharding/partitioning strategies: range vs. hash.** (Sharding concept itself covered in prior report; this focuses on the two dominant key-selection strategies.)
- *Range-based*: shard key ranges map to shards (e.g., user IDs 1–100k → Shard A). Efficient for range queries but prone to hotspots when data isn't uniformly distributed — e.g., recently-created records all landing on the newest shard ([MongoDB-oriented overview via dev.to](https://dev.to/matt_frank_usa/database-sharding-horizontal-scaling-strategies-3b07)).
- *Hash-based*: a hash function on the shard key determines placement, giving better distribution but making cross-shard range queries harder ([gocodeo](https://www.gocodeo.com/post/database-sharding-strategies-horizontal-vs-vertical-partitioning-explained)).
- *Consistent hashing* is the specific technique used in both load balancers and sharded caches/databases to minimize reshuffling when nodes are added/removed — only a fraction of keys remap instead of nearly all of them, and it also enables session/cache affinity for the same key ([Medium — Priyanshu Rajput](https://medium.com/@priyansu011/load-balancing-demystified-round-robin-least-connections-consistent-hashing-73dcc2335ef2); [Codelit](https://codelit.io/blog/load-balancing-algorithms-guide)).

**Caching layers and read replicas.** These reduce load on the primary datastore by absorbing repeat reads (cache) or offloading read traffic to secondary copies (read replicas) — both are load-shedding, not partitioning, techniques and are typically layered on top of sharding rather than replacing it.

**Load balancing algorithms.** Round robin is a simple, predictable default for stateless, homogeneous backends. Least-connections adapts better to variable or long-lived-connection workloads by routing to the currently-least-busy node. Consistent hashing is used specifically when request affinity matters (caching, sharded backends) because it keeps the same key routed to the same node while minimizing redistribution on scale-events ([oneuptime](https://oneuptime.com/blog/post/2026-02-20-load-balancing-algorithms/view); [Codelit](https://codelit.io/blog/load-balancing-algorithms-guide)).

**Async/queue-based decoupling.** Message queues/brokers (Kafka, SQS, RabbitMQ) decouple producers from consumers so each can scale independently and a slow/unavailable downstream service doesn't cascade into an upstream failure — the queue simply buffers ("if a dedicated email service goes offline, the user-registration service does not fail; it drops a message and moves on") ([Medium — Yashaman Srivastava](https://medium.com/@yashamansrivastava1710/asynchronous-communication-and-the-role-of-message-queues-in-modern-software-systems-3407ac7895d7)). This also absorbs traffic spikes: producers publish at burst rate while consumers drain at a sustainable steady rate, which is the core backpressure mechanism ([Kestra](https://kestra.io/resources/infrastructure/message-queue); [DataCamp Kafka vs SQS](https://www.datacamp.com/blog/kafka-vs-sqs)). Kafka scales by adding brokers/partitions to reach very high throughput; SQS scales transparently as a managed service, trading raw throughput ceiling for operational simplicity ([DataCamp](https://www.datacamp.com/blog/kafka-vs-sqs)).

**Database scaling patterns.**
- *Connection pooling* — reuses a bounded set of DB connections across requests instead of opening one per request, which is necessary because relational databases have hard connection limits that horizontal app scaling would otherwise exhaust quickly.
- *Read/write splitting* — writes go to a primary, reads are distributed across replicas, directly increasing read capacity at the cost of replica lag (eventual consistency for reads).
- *CQRS (Command Query Responsibility Segregation)* — separates the write model (source of truth, optimized for enforcing invariants) from the read model (optimized for query performance), typically synced via events/eventual consistency; read and write sides can then be scaled independently ([Medium — read/write splitting](https://medium.com/@maya.l.abeille.3570/cqrs-read-write-splitting-52b93cab0bdd); [Martin Fowler bliki](https://martinfowler.com/bliki/CQRS.html)). Multiple sources caution that CQRS is a targeted tool for high-read/write-asymmetry or complex-domain systems, not a default — "for most systems CQRS adds risky complexity" ([GeeksforGeeks](https://www.geeksforgeeks.org/system-design/cqrs-command-query-responsibility-segregation/)).

### Fault Tolerance

Fault tolerance techniques share a common philosophy: assume components will fail, and design so a single failure doesn't cascade or require human intervention to contain.

**Redundancy/replication and failover mechanisms.** Running multiple copies of a component is the base requirement for tolerating any single-node failure. On top of that:
- *Active-passive*: one node serves traffic, a standby monitors via heartbeat and takes over on failure. Simpler and easier to reason about consistency, but the standby is often 30–50% of infrastructure cost sitting idle, and failover has a gap where in-flight requests can be dropped ([Medium — Chaos to Clarity](https://medium.com/@sonal.sadafal/beyond-single-region-multi-region-active-active-vs-active-passive-strategies-in-aws-70e02ec1abcf); [Redis blog](https://redis.io/blog/active-active-vs-active-passive/)).
- *Active-active*: multiple nodes serve traffic simultaneously behind a load balancer; failure of one is masked by the others continuing to serve, giving near-zero downtime and better resource utilization, but requires conflict resolution and coordination (consensus/quorum) when nodes diverge, and a network partition between active-active nodes can cause both sides to accept conflicting writes that must be reconciled later ([Aerospike](https://aerospike.com/blog/active-active-vs-active-passive/); [Medium — Chaos to Clarity](https://medium.com/@sonal.sadafal/beyond-single-region-multi-region-active-active-vs-active-passive-strategies-in-aws-70e02ec1abcf)).

**Health checks and failure detection.** Load balancers and orchestrators continuously probe node/pod health; in Kubernetes specifically there are three probe types: *liveness* (is the container alive — failure triggers a restart, useful for detecting deadlocks), *readiness* (is the container ready for traffic — failure just removes it from the Service's load-balancing pool without restarting it), and *startup* (guards slow-starting containers from being killed prematurely) ([Kubernetes docs](https://kubernetes.io/docs/concepts/workloads/pods/probes/); [HackerNoon](https://hackernoon.com/kubernetes-liveness-readiness-and-startup-probes-keys-to-container-health-and-resilience)). At larger scale (e.g., distributed load balancer fleets), failure detection often uses heartbeat counters combined with gossip protocols to propagate node-health state across the fleet with eventual-consistency guarantees, rather than a single central health authority (patent filings describing production load-balancer architectures, treated here as supporting/lower-confidence evidence, not a primary spec).

**Circuit breakers.** A circuit breaker wraps calls to a potentially-failing dependency and, once failures exceed a threshold, "opens" — subsequent calls fail immediately without hitting the dependency, giving it time to recover — then periodically probes via a "half-open" state before fully closing again ([Zuplo](https://zuplo.com/learning-center/api-gateway-resilience-fault-tolerance); [DZone](https://dzone.com/articles/circuit-breaker-design-pattern-using-netflix-hystr)). The pattern was popularized in production by Netflix's Hystrix library. **Note — version/staleness flag**: Hystrix is no longer actively maintained ("more or less dead") per current sources; modern implementations use Resilience4j (Java), Polly (.NET), or built-in service-mesh (Envoy/Istio) circuit breaking instead of Hystrix ([Medium — Shinemon Divakaran](https://medium.com/@mailshine/microservices-handle-failures-using-circuit-breaker-netflix-hystrix-6e62cd831600); staleness note synthesized from search results indicating Hystrix's maintenance status).

**Retries with backoff, jitter, and idempotency.** Exponential backoff increases wait time between retries (1s, 2s, 4s...) to avoid hammering a recovering service; adding random jitter to that wait prevents synchronized retry storms across many clients ("thundering herd") ([AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/retry-backoff.html); [Temporal blog](https://temporal.io/blog/error-handling-in-distributed-systems)). Retries are unsafe unless the operation being retried is **idempotent** — otherwise a retried write can duplicate or corrupt state (e.g., double-charging a payment); this is a hard prerequisite, not optional hardening ([Temporal blog](https://temporal.io/blog/error-handling-in-distributed-systems)).

**Timeouts.** Every external call needs a bounded timeout to prevent indefinite blocking on an unresponsive dependency; common guidance is to tune timeouts slightly above observed p95 latency and adjust from real metrics rather than guessing ([Temporal blog](https://temporal.io/blog/error-handling-in-distributed-systems)).

**Bulkheads/isolation.** Named after ship compartmentalization, the bulkhead pattern assigns separate resource pools (thread pools, connection pools) per downstream dependency so that one slow/failing dependency exhausting its pool doesn't starve resources needed for calls to healthy dependencies ([GeeksforGeeks](https://www.geeksforgeeks.org/system-design/microservices-resilience-patterns/); [scalewithchintan](https://scalewithchintan.com/blog/circuit-breaker-bulkhead-retry-patterns-demystified)).

**Graceful degradation.** Systems are designed to continue functioning — possibly with reduced capability or higher latency — under partial failure rather than failing completely, e.g., falling back to a cached or simplified response when a primary dependency is down, preserving core functionality over full functionality.

**Self-healing/orchestration.** Kubernetes' controllers (ReplicaSet, Deployment, StatefulSet, DaemonSet) continuously reconcile actual state to desired state: if a pod fails a liveness probe, the kubelet sends SIGTERM, waits out the grace period, then SIGKILLs and restarts it with exponential backoff (10s up to 300s between restart attempts); if a pod dies entirely, the owning controller schedules a replacement to maintain the desired replica count ([Kubernetes docs](https://kubernetes.io/docs/concepts/workloads/pods/probes/); [Medium — Steffin Issac](https://medium.com/@iamsteffinissac/building-self-healing-pods-in-kubernetes-restart-policies-probes-and-the-pod-lifecycle-explained-960f4b076d7c)).

**Chaos engineering as validation.** Rather than waiting for production failures, chaos engineering deliberately injects failure to verify resilience assumptions hold. Netflix's Chaos Monkey randomly terminates instances in production to confirm the system tolerates it; it's part of a broader "Simian Army" (e.g., Chaos Gorilla for AZ-level outages, Latency Monkey for injected network latency), and Netflix also runs Failure Injection Testing (FIT) to inject request-level faults for specific components/user cohorts in controlled production experiments ([GeeksforGeeks](https://www.geeksforgeeks.org/system-design/what-is-netflixs-chaos-monkey/); [Gremlin](https://www.gremlin.com/chaos-monkey/the-origin-of-chaos-monkey)). The practice has since been adopted at Google, Amazon, Microsoft, LinkedIn, and Twilio among others ([Gremlin](https://www.gremlin.com/chaos-monkey)). This is best understood as a *validation* practice, not a redundancy mechanism itself — it tests whether the other fault-tolerance techniques above actually work under real conditions.

### Availability

**Redundancy across zones/regions.** AWS's Reliability Pillar guidance is explicit: distribute workloads across multiple Availability Zones (AZs) and regions to increase availability and reduce blast radius from any single failure, using multi-AZ deployments for high availability and Route 53 for DNS-level failover/traffic management ([AWS Well-Architected Reliability Pillar](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/welcome.html)). Multi-AZ protects against a single data-center-level failure (power, cooling, hardware); multi-region additionally protects against region-wide events (natural disaster, regional network/control-plane outage) but at materially higher cost and complexity.

**DNS failover.** Route 53 health checks probe an endpoint from multiple global checker locations at a configured interval; when enough consecutive probes fail to meet the failure threshold, the endpoint flips to "Unhealthy" and Route 53's failover routing policy automatically returns the secondary endpoint's IP to new DNS queries — no human action required ([Medium — SwayamOps](https://medium.com/@sharathkumarlokesh/aws-route-53-dns-failover-explained-building-resilient-applications-with-health-checks-12c06e575b53); [AWS Compute Blog](https://aws.amazon.com/blogs/compute/multi-region-event-driven-failover-architecture-with-amazon-eventbridge-and-route-53/)). A common AWS pattern is active-passive multi-region: EventBridge/API Gateway route through the primary region while Route 53 health checks monitor it and redirect to the standby region automatically on failure ([AWS Compute Blog](https://aws.amazon.com/blogs/compute/multi-region-event-driven-failover-architecture-with-amazon-eventbridge-and-route-53/)). Note this is DNS-level failover, which is inherently limited by DNS TTL/caching — clients honoring a stale cached DNS answer will not see the failover instantly, which is a practical limitation not always surfaced by vendor docs.

**Quorum-based systems.** Quorum systems (Dynamo-style, used in Cassandra, DynamoDB) parametrize replication as N (replica count), W (write acknowledgment threshold), R (read threshold); when **W + R > N**, at least one replica is guaranteed to overlap between any write set and any read set, guaranteeing read-after-write visibility of the latest committed write without requiring all N replicas to respond ([Substack — sdcourse](https://sdcourse.substack.com/p/day-28-readwrite-quorums-for-consistency); [Apache Cassandra docs](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)). Amazon's own original Dynamo production configuration was N=3, W=2, R=2 — a balanced default that neither read nor write needs to wait on every replica, and it remains the most commonly copied default across Cassandra/Riak deployments ([Java Code Geeks](https://www.javacodegeeks.com/2026/07/read-write-quorums-and-the-algebra-of-consistency-why-n-r-and-w-arent-just-configuration-knobs.html)). Quorum systems are also directly how consensus protocols (Raft/Paxos) preserve availability during network partitions: the majority partition keeps serving writes, the minority partition stops accepting writes — an explicit, engineered instance of the CAP trade-off ([Medium — Chaos to Clarity](https://medium.com/@sonal.sadafal/beyond-single-region-multi-region-active-active-vs-active-passive-strategies-in-aws-70e02ec1abcf)).

**The "nines" and downtime budgets.** Availability percentage translates directly into an allowed-downtime budget:

| Availability | Downtime / year | Downtime / month (30d) | Downtime / day |
|---|---|---|---|
| 99.9% ("three nines") | ~8h 45m | ~43m 12s | ~1m 26s |
| 99.99% ("four nines") | ~52m 34s | ~4m 19s | ~9s |
| 99.999% ("five nines") | ~5.26 min | ~26.3s | — |

(Table figures from [Hyperping's SLA/uptime pages](https://hyperping.com/three-nines), [Hyperping 99.99](https://hyperping.com/99.99), [Hyperping 99.999](https://hyperping.com/99.999).) Each additional nine cuts allowed downtime roughly tenfold. Practically: 99.9% is achievable with basic redundancy, health checks, and a disciplined deploy process, and is the common floor for SaaS/business web apps; 99.99% requires more rigorous automated recovery; 99.999% (only ~5 minutes of downtime/year) generally requires fault-tolerant architecture end-to-end, fully automated recovery, tightly controlled change processes, and every dependency in the chain also holding a compatible availability target — a single weak-link dependency (e.g., a single-region DNS provider or a manual deploy step) caps the achievable system-wide availability regardless of how resilient the rest of the stack is ([Hyperping — nine nines](https://hyperping.com/nine-nines); [Webalert](https://web-alert.io/blog/uptime-sla-explained-99-9-vs-99-99-availability)).

**Availability vs. consistency vs. cost trade-off.** This is the PACELC extension of CAP: even absent a partition, systems choose between latency and consistency during normal operation, and during a partition, between availability and consistency ([synthesized from search results; PACELC is Daniel Abadi's formalization, referenced across multiple sources including dbmsmusings.blogspot.com](http://dbmsmusings.blogspot.com/2011/12/replication-and-latency-consistency.html)). Concretely: full strong consistency across geographically distributed replicas can only be achieved by sacrificing availability and accepting higher latency, because commits must round-trip across large distances bounded by physical network transit time — pushing multi-region strong consistency toward "prohibitive" latency costs for some workloads ([synthesized from search results on consistency-latency tradeoffs](https://medium.com/@mihvoi/consistency-availability-and-low-latency-in-distributed-system-3fb72b7c02be)). Eventual consistency is the common alternative: writes are accepted immediately and propagated in the background, trading brief staleness for lower latency and higher availability. Cost compounds this: active-passive standby capacity sitting idle is a direct cost (cited estimate: standby can represent 30–50% of storage/infra cost with zero throughput contribution) ([Aerospike](https://aerospike.com/blog/active-active-vs-active-passive/)), while multi-region active-active adds ongoing cross-region data transfer and conflict-resolution engineering cost on top of the redundant compute itself.

### Real-World Examples (cross-cutting)

- **Kubernetes**: liveness/readiness/startup probes + ReplicaSet/Deployment/StatefulSet controllers give automated fault tolerance (self-healing) and, combined with HPA + Cluster Autoscaler, automated scalability ([Kubernetes docs](https://kubernetes.io/docs/concepts/workloads/pods/probes/)).
- **AWS**: Route 53 health checks + failover routing policy for availability; Auto Scaling Groups for scalability; the Well-Architected Reliability Pillar formalizes multi-AZ + automated recovery + chaos-style resilience testing as the recommended baseline ([AWS Well-Architected Reliability Pillar](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/welcome.html)).
- **Netflix**: pioneered production circuit breaking (Hystrix) for fault tolerance and pioneered chaos engineering as a discipline (Chaos Monkey / Simian Army / FIT) to continuously validate that fault tolerance and availability mechanisms actually work under real failure conditions ([Gremlin](https://www.gremlin.com/chaos-monkey/the-origin-of-chaos-monkey)).
- **Amazon Dynamo / DynamoDB / Cassandra**: the N/W/R quorum model is the canonical real-world mechanism for tuning the availability-consistency trade-off per-operation rather than system-wide ([Cassandra docs](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)).

## Trade-offs & Disagreements

- **Active-passive vs. active-active**: sources uniformly agree active-active gives better availability and resource utilization but at real complexity cost (conflict resolution, consensus); active-passive is simpler and cheaper to reason about but wastes standby capacity and has a slower, request-dropping failover gap. No source claims one is universally superior — the consistent framing across sources is "choose based on RTO/RPO targets, geographic requirements, and budget" ([CalibreOS](https://www.calibreos.com/learn/hld-multi-region); [Aerospike](https://aerospike.com/blog/active-active-vs-active-passive/)).
- **CQRS**: sources agree on the mechanical benefit (independent read/write scaling) but disagree on when it's worth it — Fowler-style architecture sources present it as a targeted tool for specific complexity/asymmetry problems, while at least one source explicitly warns it "adds risky complexity" for most systems ([GeeksforGeeks](https://www.geeksforgeeks.org/system-design/cqrs-command-query-responsibility-segregation/)). Treat CQRS as a scalability technique to reach for only when read/write patterns are genuinely asymmetric or the domain logic is complex enough to benefit from the separation — not a default database-scaling pattern.
- **Hystrix as "the" circuit breaker reference**: many tutorial-tier sources still teach circuit breakers using Hystrix, but current sources confirm it is no longer actively maintained. This is a stale-content flag — new implementations should use Resilience4j, Polly, or service-mesh-level circuit breaking (Envoy/Istio), not Hystrix itself.
- **DNS failover limitations**: vendor documentation (AWS) presents Route 53 failover as effectively instant/automatic, but this glosses over DNS TTL/caching delay on the client side — a genuine limitation of DNS-based failover as an availability mechanism that isn't a "disagreement" between sources so much as an omission in vendor framing worth flagging explicitly.
- **Five-nines practicality**: sources agree five-nines (99.999%) is achievable but describe it consistently as requiring end-to-end automation and every dependency in the chain meeting a compatible target — i.e., it's a whole-system property, not something bolted on by adding redundancy to one layer. No source disputes this; it's presented as consensus.

## Recommendation

For most production systems in a JS/TS + ExpressJS/NestJS + PostgreSQL + Drizzle/TypeORM stack (this repo's default), the pragmatic baseline is:

1. **Scalability**: keep application servers stateless (externalize session state), scale horizontally behind a load balancer with least-connections or consistent-hashing (if cache/session affinity matters), add a cache layer (e.g., Redis) in front of PostgreSQL, use read replicas for read-heavy paths, and reach for sharding/CQRS only once a single primary genuinely can't keep up — these add real operational complexity and shouldn't be adopted preemptively.
2. **Fault tolerance**: add timeouts + retries-with-jitter + idempotency keys on all external/inter-service calls first (cheapest, highest-leverage), then circuit breakers (via a maintained library, not Hystrix) around flaky dependencies, then bulkheads for the highest-risk dependencies. If running on Kubernetes, liveness/readiness probes plus controller-driven restarts give a lot of self-healing "for free."
3. **Availability**: multi-AZ deployment with automated health-check-driven failover (e.g., Route 53 + ALB health checks) is the right default target (~99.9–99.99%). Reserve multi-region active-active for workloads where the cost of downtime clearly exceeds the cost of cross-region redundancy and consistency engineering — five-nines targets are a whole-system commitment, not a single architectural decision, and should only be pursued when the business case justifies it.
4. Validate all of the above with chaos-style testing (even lightweight — e.g., manually killing an instance/pod and confirming automated recovery) before trusting it in an incident.

This would change if: the workload has hard multi-region compliance/latency requirements (data residency, sub-100ms global reads) — then active-active multi-region and quorum-tuned consistency become necessary rather than optional; or if downtime cost is provably very high per minute (e.g., payment processing at scale), which justifies investing in five-nines-grade engineering despite the cost.
