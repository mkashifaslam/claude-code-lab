## Scoping note

## Summary

A distributed system is a set of independent nodes connected over a network that must coordinate to appear as a single coherent system, built this way primarily to get **scalability** (add machines instead of a bigger machine), **fault tolerance** (no single point of failure), and **availability** (stay up despite partial failure) ([Splunk](https://www.splunk.com/en_us/blog/learn/distributed-systems.html), [GeeksforGeeks](https://www.geeksforgeeks.org/computer-networks/fault-tolerance-in-distributed-system/)). The unavoidable cost is the CAP theorem: once a network partition happens, a system must choose to sacrifice either consistency or availability — it cannot have perfect versions of both ([PingCAP](https://www.pingcap.com/article/understanding-cap-theorem-basics-in-distributed-systems/), [Cycle.io](https://cycle.io/learn/cap-theorem)). Real systems make this trade-off differently and deliberately: Google Spanner pays a latency cost (via TrueTime and commit-wait) to offer near-strong, externally consistent transactions globally ([Google Cloud](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)); Amazon's Dynamo lineage (and DynamoDB) defaults to eventual consistency and prioritizes availability, since for Amazon "inconsistency was recoverable" but downtime was not ([Medium/Shivanagouda](https://medium.com/@shivu.a.1945/i-read-amazons-dynamodb-paper-so-you-don-t-have-to-but-you-should-a2cc4239b726)); Cassandra exposes this trade-off directly to the application as a tunable consistency level per request ([DataStax docs](https://docs.datastax.com/en/cassandra-oss/3.0/cassandra/dml/dmlAboutDataConsistency.html)); Kafka and CDNs solve a related but distinct problem — distributing throughput and reducing latency via partitioning/replication and geographic caching, respectively ([Confluent](https://developer.confluent.io/courses/architecture/data-replication/), [Akamai](https://www.akamai.com/glossary/what-is-a-cdn)). The overarching lesson from every source consulted: there is no "solved" distributed system, only different, explicit trade-offs suited to different failure tolerances and latency budgets.

## Findings

### 1. What makes a system "distributed," and why build this way

A distributed system is multiple independent nodes/computers, connected by a network, that coordinate to look like one coherent system to the end user ([Splunk](https://www.splunk.com/en_us/blog/learn/distributed-systems.html)). Systems are built this way for three interlocking reasons, consistently cited across sources:

- **Scalability** — the ability to handle more load by adding machines (horizontal scaling) rather than by making one machine bigger (vertical scaling), letting capacity grow on demand ([Splunk](https://www.splunk.com/en_us/blog/learn/distributed-systems.html)).
- **Fault tolerance** — the system keeps working correctly even when individual components fail, because there is no single point of failure; a well-designed distributed system withstands the failure of one or more nodes without severe performance loss ([GeeksforGeeks](https://www.geeksforgeeks.org/computer-networks/fault-tolerance-in-distributed-system/)).
- **Availability** — the system stays reachable/usable for clients even when parts of it are unhealthy, which single-server architectures cannot guarantee ([GeeksforGeeks](https://www.geeksforgeeks.org/computer-networks/fault-tolerance-in-distributed-system/)).

These benefits are not free — see Trade-offs section — but the consensus across the sources is that once a system outgrows what one machine (or one data center) can reliably serve, distribution becomes the standard answer to all three problems simultaneously.

### 2. Core building blocks

**Nodes and networking.** Distributed systems consist of nodes (machines/processes) that communicate exclusively over a network, and the network is the fundamental source of unreliability the rest of the architecture has to work around. The classic "Fallacies of Distributed Computing" (L. Peter Deutsch, Sun Microsystems) enumerates the false assumptions engineers make — "the network is reliable," zero latency, infinite bandwidth, a secure/unchanging topology, single administrator, zero transport cost, and a homogeneous network — all of which are false in practice and drive most distributed-systems bugs ([Wikipedia](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing), [Ably](https://ably.com/blog/8-fallacies-of-distributed-computing)). Peter Bailis's widely cited ACM Queue piece "The Network is Reliable" catalogs real production partition events to make the same point empirically ([ACM Queue](https://queue.acm.org/detail.cfm?id=2655736)).

**Replication.** To survive node loss and to serve more read traffic, data is copied across multiple nodes. Replication comes in a few standard shapes — single-leader, multi-leader, and leaderless — and the core hard problem is keeping replicas in agreement about update order despite failures. Google's SRE literature frames it directly: to improve availability a service is replicated across servers, and to maintain consistency those servers must agree on every update and its order ([Google SRE Book – Managing Critical State](https://sre.google/sre-book/managing-critical-state/), as summarized via search; note: direct fetch of this page was blocked in this session by a tool-level interference, so this claim is carried at search-summary confidence rather than full-page-read confidence).

**Partitioning / sharding.** To scale beyond what replication alone can do (replication only helps with load spread and durability, not with datasets too large for one node), datasets are horizontally partitioned ("sharded") across many nodes by some shard key, so each node holds only a subset of the data ([Aerospike](https://aerospike.com/blog/database-sharding-scalable-systems/), [PlanetScale](https://planetscale.com/blog/sharding-vs-partitioning-whats-the-difference)). This is the mechanism that lets systems like Cassandra and DynamoDB hold datasets far larger than any single machine's disk.

**Consensus.** When multiple nodes must agree on a single value or ordering (e.g., "who is the leader," "what is the committed value of this log entry") despite node crashes and message loss, systems use consensus algorithms — chiefly **Paxos** and **Raft**. Raft (from Stanford) is explicitly designed to be more understandable than Paxos and is used by etcd/Kubernetes, CockroachDB, and HashiCorp Consul; Paxos is the older, more general algorithm and underlies Spanner's replication ([Charles Wan / Medium](https://charleswan111.medium.com/understanding-consensus-algorithms-cap-theorem-paxos-and-raft-2913ac2c1126), [Google Cloud on Spanner](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)).

**Load balancing.** To spread client requests across many nodes, systems place a load balancer in front of a node pool. Common algorithms: **round robin** (simple, fixed rotation, doesn't account for real load) and **least connections** (dynamic, sends new requests to the currently-least-busy server, at the cost of needing continuous connection-count monitoring) ([GeeksforGeeks](https://www.geeksforgeeks.org/system-design/load-balancing-algorithms/)).

**Failure detection.** Nodes need a way to know when a peer has died. The two standard mechanisms are: (1) centralized heartbeat monitoring, where a coordinator polls/listens for liveness signals — simple but becomes a bottleneck/single point of failure at scale — and (2) **gossip protocols**, where each node periodically exchanges membership/liveness state with a random subset of peers, so failure information propagates epidemically through the cluster without a central coordinator ([DesignGurus](https://designgurus.substack.com/p/gossip-protocols-and-heartbeats-how), [Arpit Bhayani](https://arpitbhayani.me/blogs/heartbeats-in-distributed-systems/)). Cassandra specifically uses a **phi accrual failure detector**, which outputs a confidence level rather than a binary up/down and by default only declares a node dead once ~99.9999% confident (phi threshold of 8) — this reduces false positives caused by transient network jitter ([search summary, phi accrual detector]).

### 3. The CAP theorem, consistency models, and failure modes

**CAP theorem.** Formulated by Eric Brewer and formally proven by Gilbert & Lynch, CAP states that when a network partition occurs, a distributed data store can provide at most two of: **Consistency** (every node sees the same data at the same time), **Availability** (every request gets a non-error response), and **Partition Tolerance** (the system keeps working despite dropped/delayed messages between nodes) ([PingCAP](https://www.pingcap.com/article/understanding-cap-theorem-basics-in-distributed-systems/), [Gilbert & Lynch formal paper, MIT CSAIL](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)). Because network partitions are a physical inevitability at scale, partition tolerance isn't really optional in practice — so the real-world choice is between **CP** (consistency over availability during a partition) and **AP** (availability over consistency during a partition) ([PingCAP](https://www.pingcap.com/article/understanding-cap-theorem-basics-in-distributed-systems/)).

**Strong vs. eventual consistency.** Strong consistency guarantees that after a write, every subsequent read anywhere sees that write immediately — but this requires coordination (e.g., waiting for acknowledgment from a quorum or all replicas), which raises latency and can reduce availability during partitions. Eventual consistency guarantees that, absent new writes, all replicas will *eventually* converge to the same value, allowing much lower latency and higher availability at the cost of temporarily stale reads and the need for conflict-resolution logic (e.g., last-write-wins, vector clocks, CRDTs) when concurrent writes diverge ([AlgoMaster](https://blog.algomaster.io/p/strong-vs-eventual-consistency), [Hazelcast](https://hazelcast.com/blog/navigating-consistency-in-distributed-systems-choosing-the-right-trade-offs/)). Multiple sources note this consistency/latency tradeoff exists independent of CAP — it shows up even without a partition, purely because replication itself takes time (Abadi's PACELC extension to CAP captures this, referenced across the consistency-model sources).

**Failure modes.** The two dominant failure categories distributed systems must design for are **node failures** (a machine crashes, hangs, or is unreachable) and **network partitions** (a subset of nodes becomes unable to communicate with another subset, even though each subset is internally healthy) ([Wikipedia – Fallacies of Distributed Computing](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing)). The dangerous case is that from inside a partitioned system, a "partitioned-away" node and a "crashed" node can look identical — which is exactly why systems need explicit policies (quorum, leader election, timeouts) rather than assuming failures announce themselves.

### 4. Real-world examples

**Google Spanner — chasing strong consistency globally.** Spanner partitions data across many servers worldwide and replicates each partition using **Paxos**, with each partition managed as its own Paxos group ([Google Cloud – TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)). Its key innovation is **TrueTime**, a globally synchronized clock API (backed by GPS and atomic clocks) that doesn't return a single timestamp but a *bounded uncertainty interval* guaranteed to contain the true time. Spanner uses this to assign commit timestamps and then performs a **"commit wait"** — deliberately delaying visibility of a transaction's effects until its timestamp is certainly in the past — to guarantee **external consistency**: if transaction T1 commits before T2 starts in real time, T2 is guaranteed to see T1's effects ([Google Cloud Blog](https://cloud.google.com/blog/products/databases/strict-serializability-and-external-consistency-in-spanner)). This is a direct, explicit trade of latency (waiting out clock uncertainty) for strong, global consistency.

**Amazon DynamoDB (and the original Dynamo paper) — chasing availability.** Dynamo pioneered using **consistent hashing** to spread keys evenly across nodes and tolerate node churn without a full data reshuffle. Each partition is stored on a primary node plus replicas (DynamoDB uses a primary and two secondaries); writes are acknowledged by the primary and replicated asynchronously, so a read from a secondary can briefly return stale data ([Medium/Shivanagouda](https://medium.com/@shivu.a.1945/i-read-amazons-dynamodb-paper-so-you-don-t-have-to-but-you-should-a2cc4239b726)). The original Dynamo paper's design rationale, as summarized by multiple sources, was explicit: Amazon's SLAs made availability non-negotiable while temporary inconsistency was considered recoverable — so Dynamo defaults to eventual consistency and originally used **vector clocks** for conflict reconciliation between divergent replica versions. Notably, AWS's managed DynamoDB service has since moved away from vector clocks toward **leader-based replication with Multi-Paxos per partition**, and DynamoDB today also offers an explicit strongly-consistent read option for callers willing to trade latency for correctness ([AWS docs – Read Consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)).

**Apache Kafka — partitioning and replication for throughput, not primarily for query consistency.** A Kafka topic is split into **partitions**, each hosted on a broker, so a single topic's write/read load is spread across the cluster and scales horizontally. For fault tolerance, each partition is itself replicated across multiple brokers: one replica is the **leader** (handles all reads/writes for that partition) and the others are **followers** that replicate from the leader. If the broker hosting a leader fails, one of the in-sync followers is promoted to leader automatically ([Confluent — Data Replication](https://developer.confluent.io/courses/architecture/data-replication/), [Instaclustr — Kafka Architecture](https://www.instaclustr.com/education/apache-kafka/apache-kafka-architecture-a-complete-guide-2026/)). This is a clean, concrete instance of the general "partitioning for scale + replication for fault tolerance, with a leader/follower consensus-lite protocol" pattern seen across many systems.

**Apache Cassandra — tunable consistency exposed to the caller.** Cassandra distributes rows across nodes using **consistent hashing** on the partition key, giving each node responsibility for a contiguous range on a hash ring. Rather than picking one point on the CAP spectrum for the whole system, Cassandra exposes **tunable consistency**: for every read or write, the caller specifies a consistency level (e.g., `ONE`, `QUORUM`, `ALL`) that determines how many replicas must respond before the operation is considered successful ([DataStax docs](https://docs.datastax.com/en/cassandra-oss/3.0/cassandra/dml/dmlAboutDataConsistency.html), [Instaclustr](https://www.instaclustr.com/education/apache-cassandra/apache-cassandra-database/)). This makes the consistency/availability/latency trade-off a per-request application decision rather than a fixed architectural one — arguably the most explicit real-world embodiment of the CAP trade-off among the systems surveyed here.

**CDNs — distribution for latency, not data consistency.** A content delivery network is a geographically distributed set of **edge servers** that cache copies of content close to end users; DNS-based or anycast routing sends each user's request to a nearby edge server instead of the origin, cutting round-trip latency and offloading the origin server ([Akamai](https://www.akamai.com/glossary/what-is-a-cdn), [GeeksforGeeks](https://www.geeksforgeeks.org/system-design/what-is-content-delivery-networkcdn-in-system-design/)). CDNs are a useful contrast case: they are a distributed system optimized almost purely for **latency and availability** via replication (cached copies), with a much simpler consistency model (cache invalidation/TTL) than a transactional database, because the content is largely read-heavy and tolerant of brief staleness.

### 5. Trade-offs distributed systems designers commonly face

- **Consistency vs. availability (CAP).** During a network partition, a system must choose to reject/delay requests to stay consistent (CP, e.g., Spanner's design intent) or keep serving requests and risk divergence (AP, e.g., Dynamo's default mode) ([PingCAP](https://www.pingcap.com/article/understanding-cap-theorem-basics-in-distributed-systems/)).
- **Latency vs. consistency, independent of partitions.** Even with no partition, requiring acknowledgment from more replicas (stronger consistency) means waiting on the slowest of those replicas, which is a direct latency cost — this is why Cassandra makes it a per-query dial rather than a fixed setting ([AlgoMaster](https://blog.algomaster.io/p/strong-vs-eventual-consistency), [DataStax](https://docs.datastax.com/en/cassandra-oss/3.0/cassandra/dml/dmlAboutDataConsistency.html)).
- **Complexity cost.** Sharding/partitioning adds real engineering overhead: query routing logic, difficulty of cross-shard queries/transactions, rebalancing when nodes are added/removed, and the need for conflict-resolution strategies (vector clocks, CRDTs, last-write-wins) once you accept eventual consistency ([GeeksforGeeks — Sharding vs Partitioning](https://www.geeksforgeeks.org/system-design/difference-between-database-sharding-and-partitioning/), [AlgoMaster](https://blog.algomaster.io/p/strong-vs-eventual-consistency)). None of this complexity exists in a single-node system — it is the price paid for scalability and fault tolerance.
- **Centralized vs. decentralized failure detection.** Centralized heartbeat monitoring is simpler to reason about but becomes a bottleneck and single point of failure at scale; gossip protocols scale better but add eventual-consistency-style uncertainty about cluster membership itself ([DesignGurus](https://designgurus.substack.com/p/gossip-protocols-and-heartbeats-how)).

## Recommendation

Because this was a conceptual/exploratory research task rather than a build-vs-buy decision, there is no single "adopt X" recommendation. The actionable takeaway for future design decisions: **treat CAP/consistency choice as an explicit, per-system (or even per-request, as Cassandra does) decision, not a default.** Concretely:

- Choose **CP-leaning** designs (Spanner-like strong consistency, quorum writes) when correctness of concurrent state matters more than latency or uptime during a partition — e.g., financial ledgers, inventory counts, payment state (directly relevant given this repo's FinTech/payments context).
- Choose **AP-leaning** designs (Dynamo/Cassandra-style eventual consistency) when availability and low latency matter more than momentary staleness — e.g., shopping carts, session data, activity feeds, caches.
- For read-heavy, geographically distributed static/semi-static content, a **CDN-style replicate-and-cache** approach (not a full consistency-model discussion at all) is usually the right lens, not CAP.

This would change if a specific system/workload were named — for a payments-adjacent use case in particular (per this repo's domain focus), the next research step would be a follow-up report specifically on consistency guarantees needed for payment/ledger state (e.g., idempotency keys, saga patterns, distributed transactions) rather than general distributed-systems theory.
